# LIME Engine — Method Notes (draft for report)

## 1. General LIME formulation

```
ξ(x) = argmin_{g∈G} L(f, g, π_x) + Ω(g)
```

This project implements each term of this formulation as a separate, decoupled
module (`Sampler`, `Kernel`, `LocalSurrogate`, `LimeExplainer`), matching the
task's "task-agnostic engine / task-specific adapter" split.

## 2. Term-by-term mapping

| Formula term | Role | Implementation |
|---|---|---|
| `f` | the black-box model being explained | `predict_fn`, supplied by the adapter; wraps the trained LSTM's forward pass into a flat scalar-output function. The engine never sees inside `f`. |
| `x` | the single instance being explained | raw input passed into `LimeExplainer` |
| `π_x` | proximity/weighting function — how much to trust a given perturbation based on its distance from `x` | `Kernel` class: `w_i = exp(-d_i² / σ²)`, computed from the squared mask-distance provided by `Sampler` |
| `g` | the interpretable local model | implicit — the linear model defined by the coefficient vector `β` produced by `LocalSurrogate`. `G` (the family `g` is chosen from) is restricted to linear models only, no model-class search is performed — consistent with the vast majority of LIME implementations. |
| `L` | fidelity loss between `f` and `g`, weighted by `π_x` | not implemented as an explicit loop/objective; **implicitly minimized** by the closed-form weighted ridge solution `β = (XᵀWX + λI)⁻¹XᵀWy`. This closed form is the analytic minimizer of the weighted squared-error loss `L(f,g,π_x) = Σ_i π_x(z_i)·(f(z_i) - g(z_i))²`, so no explicit optimization step is needed. |
| `Ω(g)` | complexity penalty on `g` — normally enforces sparsity / a small number of active features | **simplified**: replaced with an L2 (ridge) penalty, `λ·I`, added to the regression system for numerical stability. This does *not* reproduce the sparsity behavior of the original LIME (which typically uses Lasso / K-Lasso feature selection to zero out all but K coefficients) — ridge shrinks coefficients toward zero but does not force any of them to exactly zero. |

## 3. Where the perturbation/masking step fits

The `z` values referenced in `L` and `π_x` above (interpretable representations
of perturbed samples) are generated by `Sampler`, using binary feature masking
rather than continuous additive noise:

```
z_i ~ Binomial(1, feature_frac) over each feature dimension
neighbour_i = z_i * x + (1 - z_i) * baseline
```

This is standard LIME sampling for tabular data (Ribeiro et al., 2016):
each feature is independently kept at its original value ("on", `z=1`) or
replaced with a baseline value ("off", `z=0`). The mask `z_i` itself — not the
raw perturbed value — is what `LocalSurrogate` regresses on, which is what
keeps the resulting coefficients `β` comparable across features regardless of
each feature's original scale (important for our two domains: weather
variables and COVID case counts live on very different numeric scales, but
the engine treats both identically because it only ever sees 0/1 masks).

Distance for the kernel step is measured in mask space, not raw feature
space: `d_i² = Σ(z_i - 1)²`, i.e. the number of features toggled off. This
keeps `π_x` — and therefore the whole local-fidelity notion — consistent with
what `g` is actually being fit on (masks), rather than mixing two different
notions of "distance."

## 4. Relationship to KernelSHAP

The Sampler → Kernel → LocalSurrogate pipeline built here shares its core
skeleton with KernelSHAP (Lundberg & Lee, 2017): both perturb an instance via
binary feature masks, weight each perturbation by a kernel function, and fit
a weighted linear regression to obtain per-feature attributions. This is not
a coincidence — KernelSHAP was derived by showing that a specific choice of
sampling distribution and kernel, applied to this same LIME-style procedure,
yields coefficients that provably equal Shapley values.

This project implements the general LIME version, not KernelSHAP, and the
two differ in three specific places:

| Component | This project (LIME) | KernelSHAP |
|---|---|---|
| Mask sampling distribution | each feature independently on/off with fixed probability `feature_frac` (`Binomial(1, feature_frac)` per feature) | subsets sampled from a distribution weighted by subset *size* — very small and very large subsets are favored, over the whole combinatorial space of `2^d` subsets |
| Kernel weight | tunable, arbitrary-choice exponential kernel: `w_i = exp(-d_i²/σ²)`, with `σ` a free hyperparameter | fixed, theoretically derived "Shapley kernel," not tunable — its exact form is what makes the least-squares solution equal exact Shapley values |
| Regularization / `Ω(g)` | ridge (L2), needed for numerical stability given a modest sample count and correlated mask features (see §4 below) | typically none — under (near-)exhaustive subset sampling, the unregularized weighted least-squares solution already converges to exact Shapley values by construction |
| Guarantee on output | locally faithful in a weighted-least-squares sense; no formal fairness/uniqueness guarantee on how credit is split between correlated features | provably satisfies the Shapley axioms (efficiency, symmetry, dummy, additivity) — attributions sum exactly to `f(x) - f(baseline)` |

Both are, therefore, best described as members of the same additive-feature-
attribution family, with KernelSHAP being LIME's masking/weighting scheme
specialized to one particular kernel and sampling distribution that happens
to carry a game-theoretic guarantee. Implementing the Shapley kernel itself
was intentionally left out of scope for this build (grouped with K-LIME /
Anchor as a literature-review topic, per the task brief), so this project
should be described as a from-scratch LIME implementation, with KernelSHAP
noted only as related work / theoretical context — not as something this
codebase reproduces or claims equivalence to.

## 4b. Extended explanation of the masking step

Two masking strategies were considered for `Sampler` during development:

**Continuous additive noise** (initial version): `neighbour = x + noise`,
where `noise` is drawn from a zero-mean Gaussian scaled by a `noise_frac`
parameter, with perturbations outside a radius `r` rejected. This is a valid
perturbation strategy in principle, but has two practical drawbacks for this
project: (1) the resulting `X` matrix used in `LocalSurrogate` is in raw
feature-value space, so coefficients `β` are not directly comparable across
features with different natural scales (e.g. temperature vs. case counts);
(2) it requires a rejection-sampling loop with no guaranteed termination
unless the noise scale is bounded relative to `r`.

**Binary feature masking** (final version, standard for tabular LIME):
each feature `j` of `x` is independently assigned `z_j ∈ {0,1}` via
`z_j ~ Binomial(1, feature_frac)`. The perturbed instance actually sent to
`f` (the model) is then

```
neighbour = z ⊙ x + (1 - z) ⊙ baseline
```

(`⊙` = elementwise product) — i.e. features with `z_j = 1` keep their real
value from `x`; features with `z_j = 0` are replaced by a domain-appropriate
`baseline` (mean, zero, or a historical sample, chosen by the adapter). The
mask `z` — not `neighbour` — is what gets stacked into the `X` matrix used by
`LocalSurrogate`. This means `β_j` is interpreted uniformly as "the effect of
switching feature `j` from baseline to its real value," regardless of what
that feature's real scale is — which is what makes coefficients comparable
across features and reusable, unchanged, across both the weather and COVID
domains (satisfying the task brief's "engine reusable unchanged" constraint).

Distance for the `Kernel` step is likewise measured in mask space rather than
raw feature space: `d_i² = Σ_j (z_{i,j} - 1)²`, i.e. simply a count of how
many features were switched off in perturbation `i`. A perturbation that
keeps most features at their real value (few features off) is treated as
"close" to `x`; one that replaces most features with baseline is treated as
"far." `feature_frac` controls the average number of features switched off
per sample and therefore, indirectly, how tightly the sampled neighbourhood
clusters around `x` — playing the same conceptual role the old `noise_frac`
played in the rejected continuous-noise design, but expressed as a
per-feature toggle probability rather than a noise magnitude.

## 5. Scope decision to state explicitly in the report

We deliberately replaced LIME's typical sparsity-inducing `Ω(g)` (K-Lasso /
feature selection) with L2 ridge regularization. This was a scope choice, not
an oversight:
- keeps the solution closed-form and solvable via `np.linalg.solve` (no
  iterative optimizer needed, consistent with the "plain NumPy, closed-form"
  constraint in the task brief)
- avoids the added complexity of implementing feature-selection /ridge Lasso
  from scratch, which was explicitly out of scope for this build (grouped
  with K-LIME/Anchor as literature-review-only topics)
- trade-off: explanations from this engine will generally have small nonzero
  weights on *every* feature rather than a clean sparse subset; this should be
  acknowledged as a limitation when presenting results, and is a natural
  "future work" pointer toward Lasso-based `Ω(g)` if pursued later
